# 1. 本書の目的

本書はHuney Webサイトで扱うコンテンツおよびデータの構造を定義する。

HuneyのMVPではデータベースを利用せず、GitHub上のMarkdown / MDXファイルおよび静的データを中心としてコンテンツを管理する。

本書では主に以下を定義する。

- プロジェクトディレクトリ構成
- コンテンツディレクトリ構成
- 記事データ構造
- 用語辞典データ構造
- 動画データ構造
- カテゴリデータ構造
- frontmatter仕様
- MDX仕様
- slug仕様
- 下書き管理
- おすすめ記事管理
- 関連コンテンツ管理
- 画像管理
- YouTube情報管理

データの取得・検索・関連記事判定等の具体的な処理については処理設計書で定義する。

# 2. データ管理基本方針

MVPではDBを使用しない。

コンテンツはGitHubリポジトリ内のファイルとして管理する。

基本構成は以下とする。

```text
GitHub Repository
│
├── application source
│
├── content
│   ├── articles
│   ├── glossary
│   └── videos
│
└── public
    └── images
```

コンテンツファイルをGit管理することで、

- 変更履歴
- バックアップ
- レビュー
- 差分確認
- ロールバック

をGitHub上で行える構成とする。

# 11. 新着記事の取得ルール

トップページの「新着記事」は、公開済み記事の一覧を `publishedAt` の降順で並べたうち、先頭から最大3件を表示する。

処理要件：

```ts
const latestArticles = getAllArticles().slice(0, 3);
```

この処理は `src/lib/articles.ts` の `getLatestArticles()` に集約する。

前提条件：

- `draft: false` の公開記事のみ対象
- `publishedAt` が有効な日付であること
- `slug` が重複していないこと
- `00_INDEX.md` / `index.md` は対象外

新規記事を公開したい場合は、上記が満たされていれば自動的に一覧・新着記事・記事詳細に反映される。

# 12. 記事アップロード時の変更ポイント

今後記事を追加する際は、以下の4箇所を確認する。

1. `content/articles` 配下に Markdown ファイルを作成する
2. frontmatter の必須項目を記入する
   - `title`
   - `slug`
   - `description`
   - `publishedAt`
   - `category`
   - `draft`
3. `draft` を `false` にして公開対象にする
4. `slug` は URL で使うので、英数字とハイフンのみを使用し、一意にする

補足：

- カテゴリ名は記事一覧のフィルタに使われるため、既存のカテゴリ名と揃える
- `00_INDEX.md` はカテゴリの目次であり、記事データには含めない
- 記事本文に `#` や見出しなどを入れてMarkdownとして記述する
- 変更後は `npm run validate:content` と `npm run build` で確認する

この設計により、記事ファイル追加だけで一覧・詳細・新着表示が自動で反映される。
| relatedArticles | 関連記事 |
| seoTitle | SEO用タイトル |

画像・動画を設定しなくても記事を公開できること。

# 11. slug仕様

slugはコンテンツを一意に識別する文字列とする。

ルール：

- 英小文字
- 数字
- ハイフン
- 空白禁止
- 日本語禁止
- 原則公開後に変更しない

例：

```text
vlan
dns
amazon-s3
zero-trust
tcp-ip
three-tier-separation
```

---

# 12. slug一意性

記事内ではslugが重複しないこと。

以下は禁止する。

```text
articles/vlan.mdx
articles/vlan.mdx
```

記事と用語辞典ではURL空間が異なるため、同一slugを許可する。

例：

```text
/articles/vlan
/glossary/vlan
```

---

# 13. 公開日

`publishedAt`は以下の形式を基本とする。

```text
YYYY-MM-DD
```

例：

```text
2026-08-19
```

---

# 14. 更新日

記事を大きく修正した場合は`updatedAt`を更新する。

軽微な誤字修正等について更新日の変更を必須としない。

---

# 15. 下書き管理

記事は`draft`で公開状態を管理する。

```yaml
draft: true
```

の場合：

- 記事一覧に表示しない
- 検索結果に表示しない
- sitemapに含めない
- 関連記事に含めない
- 本番環境から閲覧させない

公開時：

```yaml
draft: false
```

とする。

---

# 16. おすすめ記事管理

MVPではアクセス数による自動ランキングを行わない。

運営者が明示的におすすめ記事を指定する。

```yaml
recommended: true
```

トップページでは、

```text
recommended = true
AND
draft = false
```

の記事を対象とする。

表示件数の制御については処理設計で定義する。

# 17. タグ

記事には複数のタグを設定できる。

例：

```yaml
tags:
  - VLAN
  - L2
  - スイッチ
```

タグはカテゴリより細かい分類に使用する。

タグ数を過度に増やさない。

目安：

```text
1記事あたり 1〜5個程度
```

# 18. カテゴリ

カテゴリはサイト全体で共通管理する。

記事ごとに原則1カテゴリを設定する。

初期カテゴリ：

```text
server
security
```

# 19. Category型

```ts
type Category = {
  id: string
  name: string
```

例：

```ts
{
  id: "network",
  name: "ネットワーク"

```

# 20. カテゴリ定義

カテゴリは個々の記事ファイルへ表示名まで重複して記述せず、共通定義から取得する。

想定：

```text
config/
└── categories.ts
```

概念例：

```ts
export const categories = [
  {
    id: "network",
    name: "ネットワーク"
  },
  {
    id: "security",
    name: "セキュリティ"
  }
]
```

---

# 21. カテゴリ追加

新しいカテゴリが必要になった場合は共通カテゴリ定義へ追加する。

記事側ではカテゴリIDのみ指定する。

```yaml
category: network
```

これによりカテゴリ表示名の変更を一括管理可能とする。

# 22. 関連記事

例：

```yaml

  - layer2-switch
```

# 23. 関連記事の考え方

関連記事は以下の優先順位を想定する。

1. `relatedArticles`による明示指定
2. 同カテゴリ
3. 共通タグ

具体的な判定・補完処理は処理設計書で定義する。

# 24. YouTube関連情報

記事に対応する動画が存在する場合のみ設定する。

例：

```yaml

```

動画が存在しない場合は`youtube`自体を記述しない。

# 49. データ整合性

ビルド時または開発時に以下を検証できる構成が望ましい。

- 必須frontmatterが存在する
- slug形式が正しい
- slugが重複していない
- categoryが存在する
- 日付形式が正しい
- relatedArticlesの参照先が存在する
- relatedTermsの参照先が存在する

# 50. 不正データの扱い

必須項目が不足しているコンテンツを正常な公開記事として扱わない。

開発時にエラーを把握できることを優先する。

任意項目が存在しないことはエラーとしない。

- 決済

ただし、記事・用語等のコンテンツまで必ずDBへ移行する必要はない。

コンテンツとユーザーデータを分離して考える。

---

# 57. CMS移行への考慮

記事数・運営人数が増加し、Gitベースの投稿が負担になった場合はCMS導入を検討する。

MVPではCMSを導入しない。

移行時にも、

- title
- slug
- description
- category
- tags
- publishedAt
- content

等の基本概念を維持できる設計とする。

---

# 58. 設計上の重要方針

## 1. テキストだけで公開できる

画像・動画は任意とする。

## 2. コンテンツとプログラムを分離する

記事追加のためにアプリケーションコードを変更しない構成を目指す。

## 3. GitHubをデータ管理の正とする

MVPではGitHub上のコンテンツを正式データとする。

## 4. 任意項目を増やしすぎない

運用開始時から複雑なfrontmatterを要求しない。

## 5. 将来変更できる

DB・CMS・外部画像ストレージへ移行可能な構造を維持する。

# 59. MVP記事の最小構成

記事を公開するために最低限必要なデータを以下とする。

```yaml
title: "VLANとは？初心者向けにやさしく解説"
slug: "vlan"
description: "VLANについて初心者向けに解説します。"
publishedAt: "2026-08-19"
category: "network"
draft: false
```

これにMDX本文が存在すれば公開可能とする。

つまり、

```text
サムネイルなし
画像なし
YouTubeなし
タグなし
関連記事なし
```

でも正常な記事として扱う。

# 60. 記事の拡張例

必要になった場合のみ情報を追加する。

```yaml
title: "VLANとは？初心者向けにやさしく解説"
slug: "vlan"
description: "VLANについて初心者向けに解説します。"
publishedAt: "2026-08-19"
updatedAt: "2026-08-20"
category: "network"

tags:
  - "VLAN"
  - "L2"

draft: false
recommended: true

thumbnail: "/images/articles/vlan/thumbnail.webp"

youtube:
  title: "VLANを図で理解しよう"
  url: "YouTube動画URL"

relatedArticles:
  - "layer2-switch"
  - "layer3-switch"
```

「必要になったものだけ追加する」という運用を基本とする。
