# 1. 本書の目的

本書は、Huney Webサイトで扱う記事・用語辞典・動画等のデータについて、取得、加工、検索、関連付け、表示判定等の処理仕様を定義する。

本書では主に以下を扱う。

- 記事取得処理
- 単一記事取得処理
- 用語取得処理
- 動画取得処理
- 公開・下書き判定
- 並び替え
- カテゴリ絞り込み
- 検索
- おすすめ記事
- 関連記事
- 関連用語
- 読了時間
- 目次生成
- Optional項目の表示判定
- データ検証
- 404判定
- データ取得失敗時の基本処理

---

# 2. 処理基本方針

HuneyのMVPではDBを利用せず、GitHubリポジトリ内のMDX・静的データを取得して画面表示する。

処理は可能な限り以下の考え方とする。

```text
ファイル読み込み
↓
frontmatter解析
↓
データ検証
↓
公開対象判定
↓
必要な加工
↓
画面表示
```

静的コンテンツ中心であるため、不要なクライアント側処理を増やさない。

---

# 3. 処理配置方針

データ取得・加工処理は `lib` 配下へ配置する。

想定：

```text
lib/
├── articles.ts
├── glossary.ts
├── videos.ts
├── categories.ts
├── search.ts
└── content-utils.ts
```

役割例：

```text
articles.ts
→ 記事取得・関連記事

glossary.ts
→ 用語取得・関連用語

videos.ts
→ 動画取得

search.ts
→ サイト内検索

content-utils.ts
→ 共通処理
```

---

# 4. 記事一覧取得処理

公開済み記事をすべて取得する処理を用意する。

概念関数：

```ts
getAllArticles()
```

処理フロー：

```text
content/articles を取得
↓
対象MDXを列挙
↓
各ファイルを読み込む
↓
frontmatter解析
↓
必須項目検証
↓
draft判定
↓
公開記事のみ抽出
↓
公開日の降順でソート
↓
Article一覧を返却
```

---

# 5. 記事一覧の公開条件

以下をすべて満たす記事のみ一般公開対象とする。

- frontmatterが正常
- 必須項目が存在
- `draft = false`
- slugが有効
- publishedAtが有効

下書き記事は本番の一覧に含めない。

---

# 6. 記事並び順

記事一覧は原則として公開日の新しい順とする。

優先：

```text
publishedAt DESC
```

公開日が同じ記事については、安定した順序になるようslug等で補助ソートしてもよい。

概念関数：

getArticleBySlug(slug)

処理：

```text

対応MDX検索
↓
ファイル読み込み
↓
frontmatter解析
↓
検証
↓
draft判定
↓
本文取得
↓
追加情報算出
↓
Article返却
```

# 8. 記事不存在時

以下の場合は記事不存在として扱う。

- 対応ファイルがない
- slug不正
- frontmatterが不正
- 本番環境でdraft
- 必須情報不足

画面側では404へ遷移させる。

---

# 9. 記事の追加算出情報

記事取得時に必要に応じて以下を追加算出する。

- 読了時間
- 目次
- カテゴリ表示名
- 関連記事
- YouTube表示可否
- OGP情報

すべてをfrontmatterへ手入力する必要はない。

---

# 10. カテゴリ絞り込み

記事一覧ではカテゴリIDにより絞り込み可能とする。

概念関数：

```ts
getArticlesByCategory(categoryId)
```

処理：

```text
公開記事一覧取得
↓
article.category === categoryId
↓
該当記事返却
```

存在しないカテゴリIDの場合は0件として扱うか、画面仕様に応じて404とする。

MVPでは0件表示でも可とする。

---

# 11. 新着記事取得処理

トップページの新着記事は、公開済み記事一覧を `publishedAt` の降順で並べた先頭3件を取得する。

概念関数：

```ts
getLatestArticles(limit = 3)
```

処理フロー：

```text
getAllArticles()
↓
公開済み記事をソート
↓
slice(0, limit)
↓
ArticleCardへ渡す
```

この処理により、記事追加時に新着記事の表示順が自動的に更新される。

実装上は `src/app/page.tsx` で `getLatestArticles(3)` を呼び、`ArticleCard` を3件分展開して表示する。

---

# 12. 記事公開フロー

新規記事を公開するまでの基本フローは以下とする。

```text
Markdown作成
↓
content/articles 配下へ配置
↓
frontmatterを記述
↓
slug / publishedAt / category / draft を確認
↓
validate:content を実行
↓
build を実行
↓
記事一覧と新着記事に反映
```

必須確認事項：

- `00_INDEX.md` ではなく実記事ファイルである
- `draft: false` である
- `publishedAt` が適切である
- `slug` が重複していない
- `category` が定義済みカテゴリと一致している

このルールを守ることで、記事一覧・詳細ページ・新着記事の3箇所が一貫して更新される。

# 13. タグ絞り込み

MVPで実装する場合はタグ一致の記事を抽出する。

概念：

```ts
getArticlesByTag(tag)
```

比較時は必要に応じて大文字小文字や表記揺れを考慮する。

ただしMVPでは複雑な正規化処理を必須としない。

---

# 12. おすすめ記事取得

`recommended: true` の公開記事を取得する。

概念：

```ts
getRecommendedArticles(limit)
```

条件：

```text
draft = false
recommended = true
```

並び順は基本的に新着順とする。

表示件数：

```text
3件程度
```

を初期値とする。

---

# 13. おすすめ記事不足時

おすすめ記事が設定されていない場合は0件を返す。

トップページ側では0件の場合にセクションを表示しない。

件数が指定数未満でも、存在する分だけ表示する。

---

# 14. 最新記事取得

トップページ用に最新記事を指定件数取得する。

概念：

```ts
getLatestArticles(limit)
```

処理：

```text
公開記事一覧
↓
publishedAt降順
↓
先頭N件
```

---

# 15. 関連記事処理

記事詳細ページで関連記事を取得する。

概念：

```ts
getRelatedArticles(article, limit)
```

基本優先順位：

1. frontmatterで明示指定された記事
2. 同カテゴリ
3. 共通タグ

---

# 16. 明示関連記事

`relatedArticles` が指定されている場合は最優先する。

例：

```yaml
relatedArticles:
  - layer2-switch
  - layer3-switch
```

指定順を表示優先順として扱う。

---

# 17. 自動関連記事補完

明示関連記事だけで表示件数に満たない場合は、自動候補で補完する。

候補スコア例：

```text
同カテゴリ       +2
共通タグ1個      +1
```

スコアの高い記事を優先する。

具体的な点数は実装時に変更可能とするが、複雑な推薦アルゴリズムは導入しない。

---

# 18. 関連記事除外条件

以下は関連記事候補から除外する。

- 現在表示中の記事
- draft記事
- 存在しないslug
- 公開対象外の記事

重複記事も除外する。

---

# 19. 関連記事件数

初期表示件数：

```text
最大3件
```

または

```text
最大4件
```

とする。

実装時は定数化することが望ましい。

---

# 20. 読了時間算出

記事本文の文字量から概算読了時間を求める。

日本語記事を中心とするため、文字数ベースを採用する。

概念：

```text
本文文字数 ÷ 500
```

を分単位の目安とする。

最低値：

```text
1分
```

---

# 21. 読了時間例

本文が2,200文字の場合：

```text
2200 ÷ 500 = 4.4
```

切り上げて、

```text
約5分
```

と表示する。

コードブロック等をどこまで文字数へ含めるかは実装の簡潔さを優先する。

---

# 22. 目次生成処理

記事本文中の見出しから目次を生成する。

対象：

```text
h2
h3
```

概念データ：

```ts
type TocItem = {
  id: string
  title: string
  level: 2 | 3
}
```

# 23. 見出しID

記事内見出しにはページ内リンク可能なidを付与する。

例：

```text

↓

```

日本語見出しのslug生成方法については、実装ライブラリ等を利用してよい。

# 24. 目次表示条件

以下の場合は目次を非表示にしてよい。

- 対象見出しが存在しない
- 見出し数が少なすぎる

初期基準例：

```text
h2/h3 合計2件未満
→ 非表示
```

# 32. 記事と動画の関連付け

# 33. YouTube URL検証

最低限、空文字でないことを確認する。

ただしMVPで外部APIによる存在確認までは行わない。

# 34. サイト内検索

MVPの検索は静的コンテンツを対象とした簡易検索とする。

概念：

```ts
searchContent(query)
```

検索対象：

- 記事タイトル
- article.description
- tags
- category
- 用語名
- glossary.summary

---

# 35. 検索処理フロー

```text
検索文字列取得
↓
前後空白除去
↓
小文字化等の簡易正規化
↓
記事一覧検索
↓
用語一覧検索
↓
結果統合
↓
種別付きで返却
```

---

# 36. 検索データ型

概念：

```ts
type SearchResult =
  | {
      type: "article"
      title: string
      description: string
      href: string
    }
  | {
      type: "glossary"
      title: string
      description: string
      href: string
    }
```

---

# 37. 検索文字列空の場合

`query`が空の場合は検索を行わない。

画面では、

```text
検索キーワードを入力してください。
```

等を表示する。

---

# 38. 検索結果0件

0件の場合は空配列を返す。

画面側でEmptyStateを表示する。

---

# 39. 検索の表記揺れ

MVPでは完全な表記揺れ対応を必須としない。

最低限、

- 大文字小文字
- 前後空白

程度を吸収する。

例：

```text
VLAN
vlan
```

を同等に検索可能とする。

---

# 40. Optional項目判定

以下は存在する場合のみ表示する。

- thumbnail
- updatedAt
- tags
- youtube
- relatedArticles
- relatedTerms
- ogImage
- officialName
- reading

処理側では `undefined` や空配列を許容する。

# 41. 空配列の扱い

例：

relatedArticles = []

# 43. カテゴリ表示名変換

# 48. 参照先検証

以下の参照について、存在確認できることが望ましい。

- relatedTerms

generateStaticParams()

---

# 51. Productionと開発環境

本番環境ではdraftを完全非公開とする。

ローカル環境で下書きを確認する必要がある場合は、将来的にPreview用仕組みを追加してもよい。

MVPではdraftファイルを直接ローカル確認する簡易方式でもよい。

---

# 52. キャッシュ・再生成

記事・用語はGit pushによって再ビルドされる静的コンテンツを基本とする。

そのため、MVPでは複雑なリアルタイムキャッシュ制御を必要としない。

---

# 53. 外部API依存

MVPでは記事表示のために外部APIを必須としない。

YouTubeについてもURLリンクを管理し、動画情報取得API等への依存を避ける。

これにより外部サービス障害によって記事本文まで表示不能になることを防ぐ。

---

# 54. 画像存在判定

thumbnail等は値がある場合のみ画像コンポーネントへ渡す。

未設定の場合は画像を取得しようとしない。

---

# 55. 画像読み込み失敗

サムネイル等の読み込み失敗により記事タイトルや本文を非表示にしない。

画像は補助情報として扱う。

具体的なUI処理は画面設計に従う。

---

# 56. HTML生成時の安全性

MDXは運営者自身が管理するコンテンツのみを対象とする。

一般利用者が任意のHTML・MDXを投稿する機能はMVPに存在しない。

将来ユーザー投稿を許可する場合はサニタイズ要件を再設計する。

---

# 57. 内部リンク

記事・用語間の内部リンクはHuney内URLを使用する。

例：

```text
/articles/vlan
/glossary/vlan
```

存在するコンテンツへ正しくリンクすること。

---

# 58. 外部リンク

YouTubeやGitHub等は外部リンクとして扱う。

URLのプロトコルが適切であること。

想定：

# 61. エラー処理基本方針

ユーザー起因ではないデータエラーについては、

- 開発時に発見しやすい
- 本番ユーザーには過度に技術的なエラーを表示しない

ことを優先する。

詳細は `04_SEO・エラー設計.md` で定義する。

---

# 62. ログ方針

MVPでは高度なログ基盤は導入しない。

開発時には必要に応じてconsole等でエラー確認する。

本番監視については運用開始後に必要性を確認する。

---

# 63. 処理性能方針

記事数が数十〜数百件程度であれば、ビルド時に全コンテンツを読み込む単純な方式を許容する。

記事数増加によりビルド時間や検索性能が問題になった場合に、

- インデックス生成
- CMS
- DB
- 外部検索サービス

等を検討する。

最初から複雑化しない。

---

# 64. 記事追加時の期待処理

```text
Git Push
↓

↓

↓

↓
公開
```

記事一覧等を手作業で更新しないこと。

# 66. 下書き公開時の期待処理

変更前：

```yaml
draft: true
```

変更後：

```yaml
draft: false
```

Git Push後に自動で公開対象となる。

---

# 67. 記事更新時

記事本文を変更し、必要に応じて、

```yaml
updatedAt
```

を変更する。

再デプロイ後、記事内容を更新する。

URLは変更しない。

---

# 68. データ削除時

記事ファイル削除後は該当URLが404となる。

既に外部公開した記事を削除する場合は、SEO・リダイレクトの観点から慎重に判断する。

リダイレクト設計については別途必要になった場合に追加する。

# 70. テスト観点への引き継ぎ

- 公開記事だけ一覧表示される
- draft記事が表示されない
- slugから正しい記事を取得できる
- 不存在slugで404になる
- カテゴリ絞り込みが機能する
- 関連記事から自分自身が除外される
- thumbnailなしでも表示できる
- youtubeなしでも表示できる
- 用語詳細が取得できる
- 検索0件時に正常表示される
- おすすめ記事未設定でも正常表示される
- 必須frontmatter不足を検知できる
