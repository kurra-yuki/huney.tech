# Huney プロジェクト管理ルール

**プロジェクト名：** Huney Webサイト構築プロジェクト  
**サービス名：** はちみつと学ぶIT  
**ドメイン：** huney.uk  
**管理方式：** Markdown / GitHub  
**対象：** 開発者・GitHub Copilot等のAIエージェント  
**バージョン：** Ver.1.0

---

# 1. 本書の目的

本書は、Huney Webサイト構築プロジェクトにおける開発・設計・テスト・課題・ドキュメント管理の共通ルールを定義する。

特にGitHub Copilot等のAIエージェントが実装を行う場合でも、

- 設計書
- プロジェクト管理表
- 課題管理表
- 実装
- テスト

の状態が乖離しないことを目的とする。

---

# 2. 基本原則

Huneyの開発では以下を基本原則とする。

1. 設計を確認してから実装する
2. 既存実装を確認してから変更する
3. 必要以上に仕様を変更しない
4. MVPを不必要に肥大化させない
5. 問題を発見した場合は課題として管理する
6. 作業状況をプロジェクト管理表へ反映する
7. 設計変更が発生した場合は設計書も更新する
8. 実装後は必要なテストを行う
9. 完了していない作業を「完了」にしない
10. 判断できない仕様をAIだけで決定しない

---

# 4. 各ドキュメントの役割

## ブランド

Huneyの、

- コンセプト
- 世界観
- デザイン
- キャラクター
- 発信方針

を定義する。

---

## 要件定義

Huneyが、

**「何を実現するか」**

を定義する。

---

## 基本設計

要件を、

**「どのようなシステム・画面・構成で実現するか」**

を定義する。

---

## 詳細設計

基本設計を、

**「どのように実装するか」**

まで具体化する。

---

## テスト仕様

実装が、

**「正しくできているかをどう確認するか」**

を定義する。

---

## 運用設計

公開後、

**「どのようにHuneyを維持・更新するか」**

を定義する。

---

## プロジェクト管理

**「何を、どこまで進めているか」**

を管理する。

---

## 課題管理

**「何が問題で、どういう状態なのか」**

を管理する。

---

# 5. ドキュメントの優先関係

実装とドキュメントに矛盾がある場合、原則として以下の順序で確認する。

```text
要件定義
↓
基本設計
↓
詳細設計
↓
実装
```

ただし、単純に「上位ドキュメントが常に正しい」とは判断しない。

矛盾を発見した場合は、

```text
課題登録
↓
意図確認
↓
正しい仕様を決定
↓
必要なドキュメント修正
↓
実装修正
```

とする。

AIエージェントが独断で仕様を決めない。

---

# 6. プロジェクト管理の正

プロジェクト進捗については、

```text
docs/07_プロジェクト管理/01_プロジェクト管理.md
```

を正式な管理元とする。

タスク状態を判断する場合は、このファイルを確認する。

---

# 7. 課題管理の正

課題については、

```text
docs/07_プロジェクト管理/02_課題管理.md
```

を正式な管理元とする。

過去の解決済み課題も削除しない。

---

# 8. 開発開始前の確認

実装を開始する前に以下を確認する。

1. `01_プロジェクト管理.md`
2. 対象Task
3. 関連Issue
4. 要件定義
5. 基本設計
6. 関連する詳細設計
7. 現在のソースコード

設計書を読まずに大きな実装変更を行わない。

---

# 9. Task開始

作業対象Taskが、

```text
未着手
```

の場合、

```text
進行中
```

へ変更する。

進捗率も必要に応じて更新する。

例：

```text
T-018

ステータス：
未着手 → 進行中

進捗率：
0% → 25%
```

---

# 10. 実装前差分確認

Huneyではすでに存在するコードを利用する場合がある。

そのため、実装前に、

```text
設計書
vs
現在の実装
```

を比較する。

確認項目：

- すでに実装済みか
- 一部実装済みか
- 設計と異なるか
- 不要な機能が存在するか
- 既存コードを流用できるか

---

# 11. 既存実装の扱い

既存コードが設計書と異なる場合でも、即座に削除・全面書き換えしない。

まず、

**なぜ異なっているか**

を確認する。

既存実装の方が合理的である可能性がある場合は、課題として登録し、設計変更を検討する。

---

# 12. 不要な全面書き換えの禁止

AIエージェントは、局所的な修正で対応可能な場合にプロジェクト全体を書き換えない。

以下を優先する。

```text
小さな変更
↓
既存構造の利用
↓
必要な部分のみ修正
```

大規模リファクタリングは明確な理由がある場合のみ行う。

---

# 13. MVP原則

Huney MVPでは、

**「将来的に必要になるかもしれない」**

だけを理由に機能を追加しない。

現在のMVPで不要なものは実装しない。

---

# 14. MVPで導入しないもの

現時点では原則として以下を導入しない。

- ユーザー登録
- ログイン
- 会員管理
- お気に入り
- コメント
- 学習履歴
- 問題集
- 決済
- 複雑なCMS
- 不要なAPI
- 不要なDB

必要になった時点で再設計する。

---

# 15. DB利用ルール

MVPではDBを使用しない。

記事・用語等はMarkdown / MDXを基本とする。

AIエージェントは独断で、

- PostgreSQL
- Supabase
- Firebase
- DynamoDB
- その他DB

を導入しない。

必要性を発見した場合は課題として登録する。

---

# 16. 外部サービス追加

新しい外部サービスを導入する場合は、人間の判断を必要とする。

例：

- CMS
- DB
- ストレージ
- 認証
- Analytics
- AI API
- 有料API

AIエージェントのみで導入を決定しない。

---

# 17. 有料サービス

料金が発生する可能性があるサービスを独断で追加しない。

必要な場合は、

```text
課題登録
↓
保留
↓
人間確認
```

とする。

---

# 18. 課題発見時

実装中に問題を発見した場合、

```text
docs/07_プロジェクト管理/02_課題管理.md
```

へ登録する。

---

# 19. Issue採番

新規Issueは、

```text
I-XXX
```

形式とする。

最大Issue番号 + 1を採番する。

既存番号を再利用しない。

---

# 20. TaskとIssueの連携

課題登録時は関連Taskを設定する。

例：

```text
I-005
関連Task：T-018
```

プロジェクト管理表側にも、

```text
T-018
関連Issue：I-005
```

を記載する。

---

# 21. 軽微な問題

以下のような軽微な問題は、必ずしもIssue登録を必要としない。

- 誤字
- 明確なtypo
- import漏れ
- formatterによる修正
- 数分で修正できる明確な問題

ただし影響範囲が広い場合は登録する。

---

# 22. 仕様判断が必要な場合

以下はAIエージェントのみで決定しない。

- 新機能追加
- MVP範囲変更
- DB導入
- CMS導入
- 認証
- 課金
- 新しい外部サービス
- URL体系の大幅変更
- ブランド変更
- アーキテクチャ変更

必要な場合はIssueとして登録し、

```text
ステータス：保留
```

とする。

---

# 23. ブランドルール

UI・文章・画像等を変更する場合はブランドブックを確認する。

Huneyでは、

**IT知識が主役**

である。

キャラクターを必要以上に前面へ出さない。

---

# 24. 初心者向け原則

HuneyはIT初心者向けサイトである。

技術的に高度な実装より、

- 分かりやすさ
- 読みやすさ
- 迷いにくさ

を優先する。

---

# 25. 発信スタンス

Huneyでは、発信者自身も学習しながら情報を発信する。

「何でも知っている専門家」という見せ方を前提にしない。

初心者と一緒に理解していく姿勢を維持する。

---

# 26. テキスト中心原則

MVPの記事はテキストだけでも成立する設計とする。

画像は必須ではない。

動画も必須ではない。

```text
テキスト
↓
必要なら画像
↓
さらに理解したい場合はYouTube
```

を基本とする。

---

# 27. YouTubeとの役割分担

Web：

```text
読む
調べる
復習する
```

YouTube：

```text
見る
図で理解する
イメージをつかむ
```

とする。

記事を動画完成まで公開待ちにしない。

---

# 28. 実装変更の範囲

タスクを実装するときは、原則として対象Taskに必要な範囲のみ変更する。

関係のないコードを同時に大量変更しない。

---

# 29. リファクタリング

リファクタリングを行う場合は、

- なぜ必要か
- 影響範囲
- 動作への影響
- テスト範囲

を確認する。

大規模な場合は新規Taskとして管理する。

---

# 30. ファイル削除

既存ファイルを削除する場合は、本当に不要か確認する。

特に、

- 設計書
- コンテンツ
- ブランド素材
- 設定ファイル

を理由なく削除しない。

---

# 31. パッケージ追加

新しいnpm package等を追加する場合、

1. 本当に必要か
2. 標準機能で代替できないか
3. 既存packageで対応できないか
4. メンテナンス状況
5. セキュリティ

を確認する。

不要な依存関係を増やさない。

---

# 32. 秘密情報

以下をGitへCommitしない。

- API Key
- GitHub Token
- Access Token
- Password
- Secret
- 個人情報
- `.env`の秘密値

---

# 33. `.env`

秘密情報を扱う場合は環境変数を利用する。

`.env`等はGit管理対象外とする。

---

# 34. セキュリティ問題

秘密情報漏洩等を発見した場合はCritical Issueとして扱う。

通常作業より優先して対応する。

---

# 35. 実装後の確認

実装完了後、対象機能について最低限以下を確認する。

- Build
- TypeScript
- 対象画面
- 対象機能
- 関連画面
- モバイル表示
- エラー
- 必要なSEO

---

# 36. テスト仕様書

テスト方法については、

```text
docs/05_テスト/
```

のテスト仕様書を基準とする。

---

# 37. テストNG時

テストが失敗した場合、対象Taskを完了にしない。

必要に応じてIssueを登録する。

---

# 38. Task完了条件

以下を満たした場合にTaskを `完了` とする。

1. 必要な実装が完了
2. Build等が正常
3. 必要なテストが成功
4. Critical / Highの関連問題が残っていない
5. 必要な設計書更新が完了
6. プロジェクト管理表を更新

進捗率：

```text
100%
```

とする。

---

# 39. AIによる「完了」判断

AIエージェント自身で確認可能な内容については完了へ更新してよい。

人間による視覚確認・判断が必要な場合は、

```text
レビュー待ち
```

または課題側を、

```text
確認待ち
```

とする。

無理に完了扱いにしない。

---

# 40. 新規Task発見時

作業中に別のまとまった作業が必要だと判明した場合、

```text
T-XXX
```

を新規採番する。

既存Taskへ無理に詰め込まない。

---

# 41. Task追加ルール

新規Taskは、

```text
現在最大Task ID + 1
```

とする。

例：

```text
現在最大：T-034

新規：
T-035
```

---

# 42. ドキュメント更新

仕様・設計を変更した場合は、関連する設計書も更新する。

コードだけ最新で、設計書が古い状態を可能な限り避ける。

---

# 43. 軽微な実装差

以下のような変更では設計書更新を必須としない。

- 変数名変更
- 内部関数分割
- CSS微調整
- formatter
- コメント
- 内部リファクタリング

外部仕様に影響する場合は更新する。

---

# 44. Git運用

mainブランチは原則として本番へデプロイ可能な状態を維持する。

大きな変更では必要に応じてfeature/fixブランチを使用する。

---

# 45. Commit

Commitは変更内容が分かる単位とする。

例：

```text
feat: 記事検索機能を追加
fix: モバイルHeaderを修正
docs: T-018の進捗を更新
content: VLAN記事を追加
```

---

# 46. AIによるGit操作

AIエージェントがGit操作を行う場合も、既存の変更を不用意に破棄しない。

特に、

- reset
- force push
- 大量削除

等の破壊的操作は慎重に扱う。

---

# 47. Production

Productionへの変更は、可能な限り、

```text
Local
↓
Preview
↓
確認
↓
Production
```

の順で行う。

---

# 48. 本番障害

本番で重大問題が発生した場合、

**原因調査より先にサービス復旧を優先してよい。**

必要に応じて以前の正常DeploymentへRollbackする。

---

# 49. 作業終了時

AIエージェントがまとまった作業を終了するときは以下を確認する。

```text
□ 対象Taskを更新したか
□ 新しいIssueはないか
□ Issue状態を更新したか
□ 設計変更はないか
□ 必要なテストをしたか
□ 未完了作業を完了扱いしていないか
```

---

# 50. 作業結果報告

作業完了後は、人間が把握できるよう以下を簡潔に報告する。

```text
実施したこと
変更したファイル
実施したテスト
更新したTask
発生・更新したIssue
残っている確認事項
```

---

# 51. Copilot向け標準作業フロー

AIエージェントは原則として以下の流れで作業する。

```text
① 管理ルールを確認
↓
② プロジェクト管理表を確認
↓
③ 対象Taskを確認
↓
④ 関連Issueを確認
↓
⑤ 関連設計書を確認
↓
⑥ 現在の実装を確認
↓
⑦ Taskを進行中へ更新
↓
⑧ 必要な実装
↓
⑨ 問題発見時はIssue登録
↓
⑩ テスト
↓
⑪ 必要な設計書更新
↓
⑫ Task / Issue更新
↓
⑬ 作業結果報告
```

---

# 52. Copilotへの基本指示

Huneyプロジェクトで作業するAIエージェントは、以下を基本指示として扱う。

```text
Huneyプロジェクトの開発ルールに従って作業してください。

作業開始前に以下を確認してください。

1. docs/07_プロジェクト管理/03_管理ルール.md
2. docs/07_プロジェクト管理/01_プロジェクト管理.md
3. docs/07_プロジェクト管理/02_課題管理.md
4. 対象タスクに関連する設計書
5. 現在のソースコード

設計書と実装に矛盾がある場合、独断で仕様を変更しないでください。

問題を発見した場合は課題管理表へIssueを登録し、
関連Taskと相互に紐付けてください。

作業開始時にTaskを進行中へ更新し、
実装・必要なテストが完了した場合のみ完了へ変更してください。

人間による判断が必要な場合は、
完了にせずレビュー待ち・確認待ち・保留を使用してください。

MVPに不要な機能、DB、外部サービス、ライブラリを独断で追加しないでください。

作業終了時には、
実施内容・変更ファイル・テスト結果・Task・Issue・残作業を報告してください。
```

---

# 53. 人間の判断を優先する事項

以下について最終判断はプロジェクトオーナーが行う。

- Huneyのコンセプト
- ブランド
- MVP範囲
- 新機能
- 有料サービス
- DB導入
- CMS導入
- インフラ大幅変更
- 公開判断
- 記事内容
- デザインの大幅変更

---

# 54. 管理ルールの変更

本ルール自体も必要に応じて変更してよい。

ただし、管理を細かくしすぎない。

ルール追加時は、

**「このルールが本当に開発を楽にするか」**

を判断する。

---

# 55. 最重要原則

Huneyの目的は、

**プロジェクト管理を完璧にすることではない。**

目的は、

**初心者がITを学べるWebサイトを作り、継続して技術情報を発信すること**

である。

プロジェクト管理・課題管理・設計書は、その目的を実現するための道具として利用する。

管理作業が目的化しないよう注意する。
