# Huney 課題管理

**プロジェクト名：** Huney Webサイト構築プロジェクト  
**サービス名：** はちみつと学ぶIT  
**ドメイン：** huney.uk  
**管理方式：** Markdown / GitHub  
**最終更新日：** 2026-08-19

---

# 1. 目的

本ファイルは、Huney Webサイト構築・運用中に発生した問題、懸念事項、確認事項を管理するための課題管理表である。

人間だけでなく、GitHub Copilot等のAIエージェントからも参照・更新することを前提とする。

実装・テスト・運用中に問題を発見した場合、本ファイルへ課題として登録する。

---

# 2. 基本方針

以下を課題管理の基本ルールとする。

- 課題ごとに一意のIssue IDを付与する
- 発見した課題を放置しない
- 課題内容を具体的に記載する
- 関連するTask IDを記載する
- 重要度と優先度を区別する
- 対応中の課題はステータスを更新する
- 解決済み課題も削除しない
- 解決方法を記録する
- 必要に応じて再発防止策を記録する
- 設計変更が必要な場合は該当設計書を更新する

---

# 3. 課題として登録するもの

以下のような事象を課題として登録する。

## 仕様

- 要件が不明確
- 設計書間で内容が矛盾している
- 実装時に仕様を決める必要が出た
- MVP対象か判断が必要

## 設計

- 設計どおり実装できない
- 設計漏れ
- URLやデータ構造の問題
- 設計変更が必要

## 実装

- バグ
- ビルドエラー
- 表示崩れ
- 実装方法の問題
- ライブラリ関連問題

## テスト

- テストNG
- 想定結果と異なる
- ブラウザ差異
- モバイル表示問題

## インフラ

- Cloudflare
- Vercel
- DNS
- HTTPS
- huney.uk
- デプロイ

## コンテンツ

- 記事表示問題
- MDXエラー
- frontmatterエラー
- リンク切れ
- 誤情報

## SEO

- metadata不備
- sitemap
- robots
- canonical
- OGP
- noindex

---

# 4. 課題として登録しなくてよいもの

以下は原則として課題登録を必須としない。

- 単純な誤字修正
- 数分で直せる軽微なコード修正
- 作業途中の一時的なエラー
- 通常の実装作業
- プロジェクト管理表ですでに管理されている通常タスク

ただし、影響が大きい場合や後から確認する必要がある場合は登録してよい。

---

# 5. Issue ID

Issue IDは以下の形式とする。

```text
I-XXX
```

例：

```text
I-001
I-002
I-003
```

新規課題は現在の最大番号 + 1を採番する。

一度使用したIssue IDは再利用しない。

---

# 6. ステータス

使用可能なステータスは以下とする。

| ステータス | 意味 |
|---|---|
| 未対応 | 課題登録済みだが対応未開始 |
| 対応中 | 現在対応している |
| 確認待ち | 修正済みでテスト・確認待ち |
| 保留 | 判断・外部要因等により停止中 |
| 解決 | 対応および必要な確認が完了 |

独自ステータスは原則追加しない。

---

# 7. 重要度

重要度は、**「この問題が発生した場合の影響の大きさ」**を表す。

| 重要度 | 基準 |
|---|---|
| Critical | サイト停止・セキュリティ・秘密情報漏洩等 |
| High | MVP主要機能が利用できない |
| Medium | 一部機能・表示・SEO等に問題がある |
| Low | 軽微な問題・改善事項 |

---

# 8. 優先度

優先度は、**「どれだけ早く対応するか」**を表す。

| 優先度 | 意味 |
|---|---|
| 高 | 優先して対応する |
| 中 | 通常のタイミングで対応する |
| 低 | 時間があるときに対応する |

重要度と優先度は必ずしも同じではない。

例：

```text
重要度：Medium
優先度：高
```

という課題も存在する。

---

# 9. カテゴリ

以下を基本カテゴリとする。

| カテゴリ | 内容 |
|---|---|
| 仕様 | 要件・仕様に関する問題 |
| 設計 | 設計書・設計方式 |
| 実装 | コード・機能 |
| テスト | テスト結果 |
| インフラ | Cloudflare / Vercel / DNS等 |
| SEO | 検索エンジン関連 |
| コンテンツ | 記事・用語・動画 |
| セキュリティ | セキュリティ関連 |
| 運用 | 公開後の運用 |
| その他 | 上記以外 |

# 11. 課題登録例

以下は記載例であり、実際の課題ではない。

```md
| I-001 | 2026-08-20 | 実装 | モバイルでHeaderが崩れる | Medium | 高 | 未対応 | T-015,T-027 | 画面幅への対応不足 | - | iPhone幅で確認 |
```

# 12. 課題登録時のルール

新しい課題を発見した場合は以下を記載する。

必須：

- Issue ID
- 発生日
- カテゴリ
- 課題
- 重要度
- 優先度
- ステータス
- 関連Task

可能な場合：

- 原因
- 対応内容
- 備考

発見時点で原因が分からない場合、

```text
調査中
```

または

```text
-
```

としてよい。

---

# 13. 課題タイトル

課題欄には、何が問題なのか分かる内容を書く。

良い例：

```text
モバイル表示でHeaderが画面幅を超える
```

```text
draft:trueの記事が記事一覧に表示される
```

```text
Vercel ProductionでMDXのBuildが失敗する
```

悪い例：

```text
バグ
```

```text
動かない
```

```text
なんか変
```

---

# 14. 関連Task

課題がどのタスクで発生したかを記録する。

例：

```text
T-018
```

複数の場合：

```text
T-018,T-027
```

該当するTaskがない場合は、

```text
-
```

とする。

必要であれば新しいTaskをプロジェクト管理表へ追加する。

---

# 15. プロジェクト管理表との連携

課題を登録した場合、関連Task側にもIssue IDを記録する。

例：

課題管理表：

```text
I-003 → 関連Task：T-018
```

プロジェクト管理表：

```text
T-018 → 関連Issue：I-003
```

これによりTaskとIssueを相互に追跡できるようにする。

---

# 16. 課題対応フロー

基本フロー：

```text
問題発見
↓
課題登録
↓
Issue ID採番
↓
重要度・優先度設定
↓
関連Task設定
↓
調査
↓
対応
↓
テスト
↓
確認
↓
解決
```

---

# 17. ステータス更新

課題発見時：

```text
未対応
```

対応開始：

```text
対応中
```

修正完了：

```text
確認待ち
```

テスト・確認完了：

```text
解決
```

外部要因等で対応できない場合：

```text
保留
```

---

# 18. 解決条件

以下を満たした場合に `解決` とする。

1. 原因または問題内容を把握している
2. 必要な対応を行った
3. 関連機能を確認した
4. 必要なテストを実施した
5. 設計変更がある場合は設計書を更新した
6. プロジェクト管理表を必要に応じて更新した

---

# 19. 解決済み課題

解決した課題は削除しない。

例：

```text
I-004
ステータス：解決
```

として残す。

Git履歴と課題管理表から、

**「過去に何が問題になり、どう直したか」**

を確認できる状態にする。

---

# 20. 再発した場合

同じ原因による問題が再発した場合でも、新しいIssue IDを採番してよい。

その場合、備考へ過去Issueを記載する。

例：

```text
I-014

備考：
I-004と同様の事象が再発
```

---

# 21. 設計変更が必要な課題

設計変更が必要な場合は、コード修正だけで解決しない。

基本：

```text
Issue登録
↓
原因確認
↓
設計変更判断
↓
設計書修正
↓
実装修正
↓
テスト
↓
Issue解決
```

---

# 22. Critical課題

以下は原則Criticalとする。

- huney.uk全体が利用不能
- 秘密情報漏洩
- GitHub Token等の漏洩
- 不正アクセスにつながる重大問題
- 意図しない個人情報公開

Critical課題を発見した場合は通常タスクより優先して対応する。

必要に応じてProductionを切り戻す。

---

# 23. High課題

例：

- 記事が閲覧できない
- 用語辞典が利用不能
- draft記事が本番公開される
- スマートフォンでサイトが利用できない
- Production Build失敗
- HTTPS問題

MVP公開前は原則解決する。

---

# 24. Medium / Low課題

Medium：

- 一部レイアウト崩れ
- SEO設定の一部不足
- 一部リンク切れ
- 特定ブラウザのみの軽微な問題

Low：

- デザイン改善
- UI微調整
- 将来的な改善候補

MVP公開後の対応を許容する。

---

# 25. MVPリリース判定との関係

Productionリリース前に以下を確認する。

```text
Critical 未解決：0件
High 未解決：0件
```

Medium / Lowについては影響を確認したうえで残存を許容する。

---

# 26. Copilotによる課題登録ルール

GitHub Copilot等のAIエージェントは、実装・テスト中に以下を発見した場合、本課題管理表への登録を検討する。

- 設計との矛盾
- 要件不足
- 実装不能な仕様
- バグ
- Build Error
- Test Failure
- セキュリティ問題
- SEO上の重大問題
- 本番公開を妨げる問題

単純な実装作業をすべてIssue化しない。

---

# 27. Copilotが課題を発見した場合

以下の順序で処理する。

```text
1. 課題管理表を読む
2. 最大Issue IDを確認
3. 新しいIssue IDを採番
4. 課題を追加
5. 関連Taskを設定
6. プロジェクト管理表の関連Issueを更新
7. 対応を開始
```

---

# 28. Copilotが課題を解決した場合

以下を実施する。

```text
1. 修正
2. 必要なテスト
3. 課題管理表の対応内容を記録
4. ステータスを確認待ちまたは解決へ変更
5. 関連Taskの状態を更新
6. 設計変更があれば設計書更新
```

AIエージェント自身が確認できない内容について、勝手に `解決` と判断しない。

その場合は、

```text
確認待ち
```

とする。

---

# 29. 課題の自動修正

軽微で、設計変更を伴わず、対応方法が明確な問題についてはAIエージェントによる修正を許可する。

例：

- 誤字
- 明確なリンクミス
- TypeScriptの単純エラー
- 明確なレイアウト不具合

影響範囲が大きい変更については、課題として記録してから対応する。

---

# 30. AIが判断してはいけないもの

以下について不明な場合は、勝手に仕様を確定しない。

- ブランド方針
- MVP範囲の大幅変更
- 新しい外部サービス導入
- DB導入
- 認証導入
- 有料サービス導入
- 大規模アーキテクチャ変更
- 個人情報を扱う機能
- 課金機能

必要な場合は課題として登録し、人間の判断を待つ。

ステータス：

```text
保留
```

として管理する。

---

# 31. 課題からタスクが発生した場合

対応にまとまった作業が必要な場合は、新規Taskを作成する。

例：

```text
I-008
↓
「検索機能の仕様変更が必要」
↓
T-041 検索機能仕様変更
```

課題管理表：

```text
関連Task：T-041
```

プロジェクト管理表：

```text
関連Issue：I-008
```

とする。

---

# 32. 備考

備考には必要に応じて以下を記載する。

- 再現条件
- 対象ブラウザ
- 対象端末
- 関連Issue
- 外部サービス状況
- 判断待ち事項
- 将来対応予定

---

# 33. Gitとの関係

課題管理表の変更もGitで管理する。

例：

```text
docs: I-003を課題管理表へ追加
```

```text
fix: I-003 モバイルHeader問題を修正
```

```text
docs: I-003を解決へ更新
```

Commit MessageへのIssue ID記載は推奨とするが、MVPでは必須としない。

---

# 34. GitHub Issuesとの関係

MVPではMarkdown課題管理表を正式な管理元とする。

GitHub Issuesは必須としない。

将来的に、

- 開発人数増加
- Issue数増加
- 自動化
- Pull Request連携

等が必要になった場合はGitHub Issuesへの移行を検討する。

---

# 35. 管理上の原則

課題管理表の目的は、課題を大量に登録することではない。

重要なのは、

**「何が問題なのか」**

**「どのTaskに影響しているのか」**

**「今どういう状態なのか」**

**「どう解決したのか」**

を後から確認できることである。

管理作業そのものがHuney開発の負担にならないよう、必要十分な粒度で運用する。
