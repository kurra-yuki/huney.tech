# Huney 運用設計書

**プロジェクト名：** Huney Webサイト構築プロジェクト  
**サービス名：** はちみつと学ぶIT  
**ブランド名：** Huney  
**ドメイン：** huney.uk  
**バージョン：** Ver.1.0  
**工程：** 運用設計  

---

# 1. 本書の目的

本書は、Huney Webサイトを本番公開した後に、安定して継続運用するための基本ルールを定義する。

主な対象は以下とする。

- 記事公開
- 記事修正
- 用語辞典更新
- 動画追加
- Git / GitHub運用
- デプロイ
- 障害対応
- バックアップ
- SEO運用
- 古い記事の更新
- コンテンツ品質管理
- セキュリティ管理
- 定期確認

---

# 2. 運用基本方針

Huneyでは以下を運用上の基本方針とする。

1. コンテンツ制作を最優先する
2. 運用作業を複雑化しない
3. GitHubをソースおよびコンテンツ管理の正とする
4. 変更履歴を残す
5. 問題発生時に以前の状態へ戻せるようにする
6. 古い情報を可能な範囲で更新する
7. 初心者向けの分かりやすさを維持する
8. 完璧を求めすぎて記事公開を止めない

---

# 3. 運用対象

Huney運営者は以下を管理する。

- Webアプリケーション
- 記事
- 用語辞典
- 動画情報
- カテゴリ
- タグ
- ブランド素材
- 必要な記事画像
- GitHubリポジトリ
- Vercel
- Cloudflare
- ドメイン
- SEO関連設定

# 4. 運用体制

MVPでは1名での運用を想定する。

役割を以下のように整理する。

## コンテンツ担当

- テーマ決定
- 調査・学習
- 記事作成
- 用語辞典作成
- YouTube制作
- 記事修正

## 開発担当

- Webサイト修正
- バグ対応
- 機能追加
- ライブラリ更新

## インフラ担当

- ドメイン
- DNS
- Vercel
- Cloudflare
- HTTPS
- 障害確認

MVPでは同一人物がすべて担当する。

---

# 5. コンテンツ公開フロー

記事公開は以下を基本とする。

```text
テーマ決定
↓
調査・学習
↓
記事作成
↓
内容確認
↓
必要に応じて用語辞典作成
↓
ローカル表示確認
↓
Git Commit
↓
GitHub Push
↓
Preview確認
↓
Production公開
↓
公開後確認
```

画像・動画制作は記事公開の必須条件としない。

---

# 6. 記事作成

記事は `content/articles/` にMDXファイルとして追加する。

例：

```text
content/
└── articles/
    └── vlan.mdx
```

記事追加時は、原則としてアプリケーションコードを変更しない。

---

# 7. 記事公開前チェック

最低限以下を確認する。

- title
- slug
- description
- publishedAt
- category
- draft
- 本文
- 誤字脱字
- 技術内容
- 見出し構造
- 内部リンク
- 外部リンク

画像を利用する場合：

- 画像表示
- alt
- ファイルサイズ

YouTubeを設定する場合：

- URL
- 動画タイトル
- リンク先

---

# 8. 下書き運用

執筆途中の記事は、

```yaml
draft: true
```

とする。

公開準備完了後、

```yaml
draft: false
```

へ変更する。

本番環境で下書きが公開されないことを確認する。

---

# 9. 公開日

初回公開日は `publishedAt` に記録する。

```yaml
publishedAt: "2026-08-19"
```

公開後に本文を修正しても、原則としてpublishedAtは変更しない。

---

# 10. 更新日

記事内容を大きく変更した場合は `updatedAt` を更新する。

対象例：

- 技術仕様の変更
- 説明の大幅追加
- 記事構成変更
- 古い情報の更新
- 誤解を生む説明の修正

軽微な誤字修正では更新日の変更を必須としない。

---

# 11. 記事削除

公開済み記事は原則として安易に削除しない。

削除前に以下を検討する。

- 修正できないか
- 他の記事と統合できないか
- 古い記事として残せないか
- リダイレクトが必要か

検索流入や外部リンクが存在する可能性を考慮する。

---

# 12. URL変更

公開済み記事のslugは原則変更しない。

やむを得ず変更する場合は、

- 旧URL
- 新URL
- リダイレクト

を検討する。

URL変更によるリンク切れを避ける。

---

# 13. 用語辞典運用

新しい専門用語が記事内で頻繁に登場する場合、用語辞典への追加を検討する。

用語辞典では詳細記事ほど深く説明せず、

**短時間で意味を確認できること**

を優先する。

---

# 14. 用語辞典追加フロー

```text
用語決定
↓
content/glossaryへMDX追加
↓
一言説明作成
↓
初心者向け解説
↓
関連用語設定
↓
関連記事設定
↓
確認
↓
公開
```

---

# 15. YouTube運用

視覚的に説明した方が理解しやすいテーマについてYouTube動画制作を検討する。

記事公開をYouTube動画完成まで待たない。

基本：

```text
記事
↓
公開
↓
必要に応じてYouTube制作
↓
記事へ動画リンク追加
```

---

# 16. WebとYouTubeの役割

Web：

```text
読む・調べる
```

YouTube：

```text
見る・図で理解する
```

Web記事だけでも基本的な内容を理解可能とする。

---

# 17. 動画リンク更新

YouTube動画を公開した場合、

- 動画一覧
- 対応記事
- 必要に応じて用語辞典

へリンクを追加する。

---

# 18. リンク切れ

外部リンクは時間経過により無効になる可能性がある。

特に以下を定期的に確認する。

- YouTube
- ベンダー公式サイト
- GitHub
- SNS
- 公式ドキュメント

リンク切れを発見した場合は修正または削除する。

---

# 19. Git運用基本方針

GitHubリポジトリを正式なソース管理場所とする。

すべての重要変更はGitへ記録する。

直接Production環境のファイルを変更しない。

---

# 20. ブランチ運用

MVPでは複雑なGit Flowを採用しない。

基本：

```text
main
```

を本番ブランチとする。

機能開発・大きな修正では必要に応じて、

```text
feature/xxx
fix/xxx
```

等を使用する。

---

# 21. ブランチ例

```text
feature/search
feature/glossary
fix/article-layout
fix/mobile-menu
```

---

# 22. mainブランチ

mainは常に、

**本番へデプロイ可能な状態**

を維持することを目指す。

---

# 23. Commit方針

変更内容が理解できるCommit Messageを利用する。

例：

```text
feat: 記事検索機能を追加
fix: モバイルメニュー表示を修正
docs: 基本設計書を更新
content: VLAN記事を追加
```

---

# 24. Commit単位

大量の無関係な変更を1Commitへまとめすぎない。

一方で、細かすぎるCommitを大量に作ることも必須としない。

後から変更理由が把握できる粒度を優先する。

---

# 25. Pull Request

個人開発のためすべての変更でPRを必須としない。

以下の場合はPR利用を推奨する。

- 大きな機能追加
- リファクタリング
- デザイン大変更
- Copilotによる大量コード変更

Preview環境での確認に利用できる。

---

# 26. Copilot利用方針

GitHub Copilotは主に実装支援として利用する。

実装時には設計書を参照させる。

基本：

```text
企画
↓
要件
↓
基本設計
↓
詳細設計
↓
Copilot実装
↓
テスト
```

Copilotが生成したコードを無確認で本番へ反映しない。

---

# 27. AI利用方針

記事作成やコード作成にAIを利用してもよい。

ただし、

- 技術情報を確認する
- 誤りを修正する
- 自身で内容を理解する
- 文章がHuneyのコンセプトに合うか確認する

ことを前提とする。

---

# 28. デプロイ運用

基本デプロイフロー：

```text
Local
↓
GitHub
↓
Vercel Preview
↓
確認
↓
main
↓
Vercel Production
↓
huney.uk
```

---

# 29. Production公開後確認

本番反映後、最低限以下を確認する。

- トップページ
- 変更対象ページ
- 記事一覧
- 記事詳細
- モバイル表示
- リンク
- HTTPS

記事追加のみの場合は対象記事中心の確認でもよい。

---

# 30. デプロイ失敗時

Vercel Buildが失敗した場合、

1. エラーログ確認
2. 変更箇所確認
3. ローカル再現
4. 修正
5. 再Push

を行う。

原因不明の場合、直前の正常Commitへの切り戻しを検討する。

---

# 31. ロールバック

本番公開後に重大な不具合が発生した場合、以前の正常なGit CommitまたはVercel Deploymentへ戻す。

重大障害では修正より先に復旧を優先する。

---

# 32. 障害レベル

## Critical

例：

- サイト全体が表示不能
- HTTPS障害
- 秘密情報公開
- 全記事が404
- 不正コンテンツ公開

対応：

**可能な限り早く復旧**

---

## High

例：

- 記事詳細が利用不能
- スマートフォンで閲覧不能
- 大量リンク切れ
- draft公開

早めに修正する。

---

## Medium

例：

- 一部レイアウト崩れ
- 一部リンク不良
- 一部SEO情報不備

通常対応。

---

## Low

例：

- 軽微なデザイン違和感
- 誤字
- 細かなUI改善

随時修正する。

---

# 33. 障害対応フロー

```text
問題発見
↓
影響確認
↓
重大度判定
↓
Critical/Highの場合
├── Rollback検討
└── 緊急修正
↓
原因調査
↓
修正
↓
テスト
↓
再リリース
```

---

# 34. 障害記録

大きな障害については簡単な記録を残す。

例：

```text
発生日
事象
原因
対応
再発防止
```

企業レベルの詳細な障害報告書まではMVPで必須としない。

---

# 35. バックアップ

以下はGitHubで管理する。

- ソースコード
- 記事
- 用語辞典
- 動画情報
- 設定ファイル

GitHubを主要バックアップの一つとして利用する。

---

# 36. 画像バックアップ

Git管理している画像はGitHub上に保持される。

将来的にCloudflare R2等へ移行した場合は、ストレージ側のバックアップ方法を別途検討する。

---

# 37. ドメイン管理

ドメイン：

```text
huney.uk
```

について以下を管理する。

- 更新期限
- Registrar情報
- DNS
- ネームサーバー

ドメイン失効は重大障害となるため、更新を忘れないこと。

---

# 38. ドメイン更新

自動更新可能な場合は有効化を推奨する。

支払い方法・メールアドレスが無効にならないよう注意する。

---

# 39. Cloudflare運用

Cloudflareでは主に以下を管理する。

- DNS
- ネームサーバー
- 必要なセキュリティ設定

不用意にDNSレコードを変更しない。

変更前には現在値を確認する。

---

# 40. Vercel運用

Vercelでは主に以下を確認する。

- Production Deployment
- Preview Deployment
- Build Logs
- Domain
- HTTPS
- Environment Variables

---

# 41. 環境変数

秘密情報を扱う場合はVercel等の環境変数として管理する。

GitHubへ直接Commitしない。

---

# 42. `.env`

ローカル環境で利用する`.env`等は `.gitignore` 対象とする。

秘密情報を含むファイルを誤ってGitへPushしない。

---

# 43. GitHub Token等

GitHub Token、API Token等は、

- README
- 設計書
- ソースコード
- Commit履歴

へ記載しない。

漏洩した場合は直ちに失効・再発行する。

---

# 44. ライブラリ更新

利用しているNext.js等のライブラリは定期的に更新状況を確認する。

ただし、

**常に最新版へ即時更新すること**

を目的としない。

安定性・セキュリティを考慮して更新する。

---

# 45. セキュリティ更新

重大な脆弱性情報がある場合は優先して確認する。

依存パッケージの警告等を定期的に確認する。

---

# 46. SEO運用

公開後はSearch Console等を利用して検索状況を確認することを検討する。

主な確認：

- インデックス状況
- 検索キーワード
- 表示回数
- クリック
- クロールエラー

---

# 47. sitemap運用

記事・用語の追加時に自動更新される構成を維持する。

手作業でURLを追加する運用にはしない。

---

# 48. robots運用

robots設定を変更する場合は慎重に行う。

Production全体を誤ってDisallowしない。

---

# 49. noindex確認

本番記事へ誤ってnoindexが設定されていないことを、SEO関連変更時に確認する。

---

# 50. 記事SEO運用

記事公開時に最低限確認する。

- title
- description
- slug
- h1
- 見出し
- internal link
- canonical
- OGP

SEOを理由として不自然な文章にしない。

---

# 51. 外部プラットフォーム運用

Qiita、YouTube、SNS等はHuneyへの入口として利用可能とする。

Huneyをコンテンツの中心とする。

記事転載等を行う場合は重複コンテンツについて注意する。

---

# 52. コンテンツ品質管理

記事公開時の最重要確認：

**「ITを学び始めた頃の自分が読んで理解できるか？」**

Huneyのブランド方針に合わない記事は修正する。

---

# 53. 情報源

可能な範囲で一次情報を確認する。

優先例：

1. 公式ドキュメント
2. RFC・標準
3. ベンダー公式資料
4. 信頼性の高い技術資料

---

# 54. 古い記事

技術情報は時間とともに古くなる。

特に以下を優先して見直す。

- クラウド
- AI
- SaaS
- 製品仕様
- 価格
- UI操作
- 資格試験

---

# 55. 記事更新判断

以下の場合に更新を検討する。

- 内容が現在仕様と違う
- 読者から誤りを指摘された
- 自身の理解が進み説明を改善できる
- リンク切れ
- 関連サービス変更

---

# 56. 古い情報の扱い

古い記事をすぐ削除せず、

- 更新
- 注意書き追加
- 新記事へ誘導

を検討する。

---

# 57. 更新頻度

固定の更新ノルマは設定しない。

継続できることを優先する。

記事本数のために品質を大幅に下げない。

---

# 58. 定期確認

目安として定期的に以下を確認する。

## 月1回程度

- サイト表示
- ドメイン
- Vercel
- リンク切れ
- Search Console
- 主要記事

## 数か月ごと

- 古い記事
- ライブラリ
- ブランドルール
- カテゴリ
- サイトUI

厳密なスケジュールとして強制しない。

---

# 59. アクセス解析

アクセス解析を導入した場合、以下をサイト改善に利用する。

- 人気記事
- 検索流入
- ページ遷移
- デバイス
- YouTube遷移

閲覧数だけを記事価値の判断基準にしない。

---

# 60. おすすめ記事

MVPでは自動ランキングではなく、運営者が選択する。

おすすめ記事は、

- 初心者におすすめ
- 基礎として重要
- 次に読んでほしい

等の観点で選ぶ。

---

# 61. 将来の人気記事

十分なアクセスデータが蓄積した場合は、自動人気記事機能を検討する。

その時点で必要に応じてDBまたは解析データ連携を設計する。

---

# 62. DB導入判断

以下が必要になった場合にDB導入を再検討する。

- ユーザー登録
- ログイン
- 学習履歴
- お気に入り
- コメント
- 問題集
- 会員機能
- 決済

「将来使うかもしれない」という理由だけでは導入しない。

---

# 63. CMS導入判断

以下の場合にCMS導入を検討する。

- 記事投稿者が増える
- Git操作が運用負担になる
- 記事数が大幅に増える
- スマートフォン等から投稿したい
- 投稿ワークフローが必要になる

MVPではMDX運用を継続する。

---

# 64. 画像ストレージ移行判断

以下の場合は外部ストレージを検討する。

- Gitリポジトリ容量増大
- 画像数増加
- デプロイ負荷増加
- 動的画像変換が必要

候補としてCloudflare R2等を検討可能とする。

---

# 65. 機能追加ルール

新機能を追加する前に以下を確認する。

1. 本当に必要か
2. 初心者にメリットがあるか
3. 運用負荷は増えないか
4. 既存機能で代替できないか
5. MVPの思想に反していないか

---

# 66. 仕様変更

仕様を大きく変更する場合、該当する設計書を更新する。

例：

```text
要件変更
→ 要件定義書

画面変更
→ 基本設計・画面詳細設計

データ変更
→ コンテンツ・データ設計

処理変更
→ 処理設計
```

---

# 67. ドキュメント運用

設計書と実装が大きく乖離しないようにする。

軽微な実装差異まで毎回設計書を更新する必要はない。

今後の開発判断に影響する変更を記録する。

---

# 68. README

READMEには最低限以下を維持する。

- Huney概要
- 開発環境構築
- 起動方法
- 記事追加方法
- 用語追加方法
- デプロイ概要

---

# 69. 記事追加手順

README等から簡単に確認できる状態を維持する。

理想：

```text
MDXファイル追加
↓
本文作成
↓
Push
```

だけで記事公開できる状態を維持する。

---

# 70. テスト運用

大きな変更時はテスト仕様書を基準に確認する。

すべての小さな記事修正で全テストを実施する必要はない。

変更内容に応じた範囲を確認する。

---

# 71. 回帰テスト

サイト機能を変更した場合は、

- トップ
- 記事一覧
- 記事詳細
- 用語辞典
- モバイル
- 404
- SEO

等の主要機能を再確認する。

---

# 72. リリース判定

以下の場合は本番公開を止める。

- Critical障害
- 秘密情報漏洩
- draft公開
- 記事閲覧不能
- HTTPS不能

軽微なUI問題はMVPでは公開後修正を許容する。

---

# 73. 運用上の優先順位

問題や作業が複数存在する場合は以下を優先する。

# 74. Huney独自の運用原則

Huneyでは以下を大切にする。

**記事を公開するために、必要以上の準備を要求しない。**

**画像や動画がなくても、良い記事なら公開する。**

**完璧になるまで公開しないのではなく、公開後も改善する。**

**誤りを見つけたら素直に直す。**

**学んだ内容を、次に学ぶ初心者へ残す。**
